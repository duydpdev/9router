# Findings

phase-01.md:Architecture: CRITICAL `markReauthNotified` read-then-write CAS is NOT atomic. `updateProviderConnection` (src/lib/db/repos/connectionsRepo.js:157) uses `db.transaction()` but node:sqlite adapter (src/lib/db/adapters/nodeSqliteAdapter.js:64) issues a bare SAVEPOINT and better-sqlite3 defaults to DEFERRED — neither upgrades to a write lock at read time. Two concurrent fatal failures both read `reauthNotifiedAt=null`, both pass the guard, both write → two webhooks. The "race window is the read→write gap, acceptable" hand-wave fails when ~5–10 in-flight SSE handlers hit the same dead refresh in the same ~50 ms (normal). Fix: do the compare-and-set as ONE conditional UPDATE (`UPDATE providerConnections SET data=json_set(...) WHERE id=? AND json_extract(data,'$.reauthNotifiedAt') IS NULL AND json_extract(data,'$.reauthAt')=?`), dedup on `changes===1`. Same concern for `markNeedsReauth` though it is write-only so collisions are benign (last-write-wins on identical payload).

phase-01.md:reauthReason: LOW Four enum values but only two affect behavior (Phase 5 skip is binary, Phase 6 only displays the string). Collapse to two values or keep a freeform string. YAGNI.

phase-02.md:forceRefresh: HIGH On refresh-token rotation where IdP returns a new refresh token, `forceRefresh` computes `merged.refreshToken = newCreds.refreshToken ?? credentials.refreshToken` correctly, then calls `updateProviderCredentials(...newCreds)` (note: spreads `newCreds`, NOT `merged`). `updateProviderCredentials` (src/sse/services/tokenRefresh.js:159) guards `if (newCredentials.refreshToken)` — non-falsy only. Saves only fine because open-sse coalesces upstream (tokenRefresh.js:18,108,145,217,302), but the local merge order in the plan is misleading. Fix: pass `refreshToken: merged.refreshToken` explicitly to `updateProviderCredentials`, and stop relying on upstream coalesce as the safety net.

phase-02.md:retry-block: MEDIUM Inlined retry-on-401 at SSE-handler layer triggers `forceRefresh` on every 401/403 regardless of cause. A per-account 401 (rate-limit masked, IP block) will burn a refresh on every request and on Codex risks `refresh_token_reused` family revoke (open-sse/services/tokenRefresh.js:35–40, 540). Fix: only retry when response body / `WWW-Authenticate` indicates `invalid_token`/`expired_token`. The single-retry budget alone is insufficient because each request re-triggers.

phase-03.md:deep-link: HIGH "Anyone with the link still needs dashboard auth cookie" is only true when `settings.requireLogin !== false`. src/dashboardGuard.js:155–160, 248 explicitly bypass auth for `/api/*` and `/dashboard/*` when `requireLogin=false` (a common self-hosted default). In that mode, a connectionId leaking via Discord/Telegram channel logs (now-quit team member, public webhook) lets anyone trigger the OAuth flow for that exact row and replace its tokens with their own → silent identity-swap of an API account. Fix: refuse to send the deep-link when `settings.requireLogin === false`, OR include a short-lived HMAC token in the URL (`?reconnect=<id>&t=<hmac>`) that the GET authorize handler verifies.

phase-03.md:resolveBaseUrl: MEDIUM `BASE_URL` env-controlled (not user input) so no open-redirect risk inside the app, BUT the fallback to `http://localhost:20128` for cloud/tunnel deployments will silently send a worthless local URL to the webhook (looks legit, doesn't work from the user's phone). Plan flags "warn log" — upgrade to: when `BASE_URL` is unset AND `tunnelUrl` exists in settings, prefer `tunnelUrl`. Otherwise skip the notify with a clear error log instead of mailing a broken link.

phase-03.md:builders: MEDIUM `buildDiscordPayload`/`buildTelegramPayload`/`buildGenericPayload` (src/lib/warmup/notifier.js:267,300,335) read `ctx.run.error`, `ctx.schedule.name`, `ctx.connection.*` — a "reauth" `kind` will hit `ctx.run` undefined and emit `(no error message)` / "(schedule)" placeholders. Plan says "extend builders to handle kind === 'reauth'" but does not enumerate which fields each builder must learn. Risk: malformed Discord embed crashes the JSON parse on the webhook side, dropping the notify silently. Fix: write the builders' reauth branch explicitly per channel, with the same `escapeMarkdownV2` / `sanitizeDiscordMentions` calls — connection name and email are user-controlled strings.

phase-04.md:classifier: HIGH Phase 4 line 52 claims `getAccessToken` returns `{ error: "invalid_grant" }` for Codex — wrong. Codex returns `{ error: "unrecoverable_refresh_error", code: "refresh_token_reused"|"invalid_grant"|... }` (open-sse/services/tokenRefresh.js:282). The Phase 4 classifier (`input.error ?? ""`) will read `"unrecoverable_refresh_error"` and match NO pattern → returns `null` → fatal path NEVER fires for Codex, the exact provider this plan was motivated by. Fix: classifier must also match `unrecoverable_refresh_error` literal, and inspect `input.code` field when present.

phase-04.md:classifier: HIGH For Claude / Google / Qwen / iFlow / Kiro / GitHub refresh helpers, on 4xx the helper returns plain `null` (open-sse:140, 174, 236, 237) without surfacing the response body. Classifier sees `null` → returns `null` → fatal path NEVER fires. Every non-Codex provider in scope (Claude, Antigravity, Gemini-CLI, Qwen, iFlow, GitHub, Kiro) silently falls into "transient" forever. Fix: refactor the open-sse refresh helpers to return `{ error, status, body }` on 4xx (or surface via thrown error with `.status`/`.body`) before the classifier can see anything.

phase-04.md:fire-and-forget: MEDIUM `notifyReauthRequired(...).catch(log)` is unawaited. If the request handler returns and Node's event loop tears down the SSE response, the dangling promise still holds the slow webhook fetch (Discord can take 5–30 s on degraded networks). With `ProxyAgent` keep-alive sockets this leaks file descriptors and may interleave with the next request's stream. Fix: detach via `queueMicrotask(() => notifyReauthRequired(...))` AND give the webhook fetch a hard timeout (the warmup notifier already has timeout — make sure reauth uses the same `postWebhook` wrapper, not a fresh `fetch`).

phase-05.md:getActiveConnections: LOW Phase 5 names `getActiveConnections(provider)` (lines 63, 70) — this function does not exist (grep returns zero hits). The actual call is `getProviderConnections({ provider, isActive: true })` (src/sse/services/auth.js:55). Cosmetic — fix the plan text so an implementer does not chase a phantom symbol.

phase-05.md:allNeedReauth: LOW Branch ordering: plan re-queries `getActiveConnections` after filtering returns empty (line 70), then checks `every(c => c.needsReauth)` — wrong when `excludeSet` is non-empty (e.g. 3 connections, 2 excluded, 1 needsReauth → `every` is true, but the real reason "all alternates exhausted in this retry chain" is hidden). Fix: compute `allNeedReauth` from the FILTERED-FOR-excludeSet subset only.

phase-06.md:auto-trigger: MEDIUM `router.replace(window.location.pathname)` is called unconditionally including when `conn` is not found — this races the `notify.error` toast and causes the toast to fire before the URL replace, then a fast-refresh re-reads the now-stripped param and the toast disappears. Move `router.replace` inside the success branch and also inside an else after the error toast.

phase-06.md:auto-trigger: LOW `useEffect` deps `[reconnectId, connections]` — `connections` is a fresh array on every render → effect re-runs constantly even after `triggeredRef.current=true`. Fine because of the ref guard, but `router.replace` inside still fires repeatedly → Next.js logs noise. Memoize the trigger or change deps to `[reconnectId]`.

phase-07.md:state-store: CRITICAL Plan claims "OAuth state must remain unforgeable — connectionId rides inside the existing signed/random state" and "lookup session by state → recover connectionId". For Codex and xAI this works (src/lib/oauth/utils/server.js:131, 289 hold server-side sessions). For ALL other providers (`claude`, `gemini-cli`, `antigravity`, `github`, `qwen`, `iflow`, `kiro`, `cline`, `gitlab`, `qoder`, `cursor`) `generateAuthData` returns `{state, codeVerifier}` to the BROWSER — there is no server session. So `connectionId` for those providers must come from the request body, which is JS-controlled and attacker-tamperable from any same-origin XS
